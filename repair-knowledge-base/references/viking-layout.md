# Layout And Memory Sync

The knowledge base is a directory tree owned by `scripts/kb.py`.
OpenViking holds the durable mirror.

## Tree

```text
.repair-kb/
  index.md                        # generated by kb.py index
  taxonomy.md                     # hand-maintained failure_class vocabulary
  nodes/L1/<node-id>.md
  nodes/L2/<node-id>.md
  nodes/L3/<node-id>.md
  trajectories/<trajectory-id>.md
```

`kb.py query` reads `nodes/` only.
`trajectories/` is provenance and is never returned as guidance;
the directory split is what enforces that,
so do not flatten the tree.

Override the root with `--root` or `REPAIR_KB_ROOT`
to keep one shared knowledge base across repositories:

```bash
export REPAIR_KB_ROOT=~/.repair-kb
```

## Mirror To OpenViking

Memory tool names and URI schemes vary by deployment.
Browse the memory root first
and mirror the pattern you observe:

```text
viking_browse viking://user/default/memories/
viking_browse viking://user/default/memories/entities/
```

Write each changed file to
`viking://user/default/memories/entities/repair-kb/<relative path>`,
preserving the tree exactly.
Never invent a scheme.
If no write verb is exposed,
commit the tree and report that the sync is pending.

List what needs mirroring:

```bash
find .repair-kb -name '*.md' -newer .repair-kb/index.md
```

## Identifiers

Node ID:

```text
<level>-<stage-abbr>-<failure-class>-<slug>
```

Stage abbreviations:
`loc` for localization,
`plan` for planning,
`exec` for execution-verification.

Trajectory ID:

```text
traj-<YYYY-MM-DD>-<short-context>
```

IDs are lowercase,
hyphen-separated,
and stable.
The node file name must be `<node-id>.md`;
`kb.py outcome` resolves nodes by file name.
Renaming an ID breaks `parent`, `children`, and index references;
use `supersedes` instead.

## Index

`index.md` is generated, never hand-edited:

```bash
python3 scripts/kb.py index
```

It reports node counts per level,
a per-`failure_class` table with stage coverage and contributing repos,
and every node unverified for more than 180 days.
Run it after each write so the counts stay honest.

## Taxonomy

`taxonomy.md` holds the controlled vocabulary for `failure_class`.
Free-text classes fragment retrieval,
so add a term deliberately:

```markdown
## ci-metric-miscount
A reported metric is an artifact of the measurement method rather than the
system under test.
Sibling terms: measurement-validity (L3 generalization).
```

When a new repair does not fit an existing class,
add the term to `taxonomy.md` first,
then write the nodes.

## Retrieval

`kb.py query` handles scoring and filtering:

```bash
python3 scripts/kb.py query --stage localization \
    --text "<error or symptom>" --language shell --ecosystem github-actions \
    --failure-class ci-metric-miscount --budget L1=2,L2=2,L3=1
```

What it does, so the output can be trusted:

- Filters to the requested stage.
- Rejects any node whose `portability.languages` or `portability.ecosystems`
  excludes the target and is not `*`.
  This is what prevents cross-stack fabrication,
  where a Node.js node is retrieved for a Shell repository
  and the plan references files that do not exist.
- Scores `error_signatures` at 3, `symptoms` at 2, `keywords` at 1,
  adds 4 for a `failure_class` match,
  adds `verified_count` up to 3,
  and subtracts 2 per `refuted_count`.
- Returns the per-level budget, two `L1`, two `L2`, one `L3` by default.
  Mixed levels beat any single level:
  `L1`-only loses transfer,
  `L3`-only loses actionability.
- Marks nodes unverified for more than 180 days as `[STALE]`.

When the result looks lexically similar but procedurally irrelevant,
reject it manually and tighten that node's `applicable_when`.
The relevance verifier prompt in
[abstraction-prompts.md](abstraction-prompts.md)
covers that judgement.

## Outcomes

Record the result on every node the plan used:

```bash
python3 scripts/kb.py outcome --label partial NODE_ID NODE_ID
```

The command bumps `verified_count` or `refuted_count`,
refreshes `last_verified`,
and prints the field to revise for non-verified labels.
Apply that revision by editing the node —
the counter alone changes nothing about future guidance.
